# 启动性能预算与后台延后边界

**状态**: 已接受
**日期**: 2026-09-27
**修订**: 2026-09-27，根据 Issue #18 阶段 2 基线数据调整目标、体积预算和内存口径
**关联**: [Issue #18](https://github.com/runningwaterpro/milkup/issues/18)

## 背景

Milkup 的启动由 Electron/Chromium 初始化、本地资源加载、编辑器创建和若干启动期外围任务共同组成。优化可以延后部分外围工作，但不能删功能、转移等待成本或让主分支产生无法测量的性能改动。因此先固定指标、预算和延后边界，再按实测收益选择实现。

## 决策

1. **可交互时间是主指标。** 窗口可见时间和稳定就绪时间同时记录，但不为优化窗口出现而牺牲编辑器可用性。
2. **主场景 P95 至少缩短 19%（约 150ms）作为验收，25% 作为挑战目标。** 阶段 2 基线显示应用层可控部分约 372ms，因此 19% 是可验收的下限，25% 不再作为硬性合并门槛，但继续作为优化目标。单项优化必须同时节省至少 50ms、提升至少 3%，并在两次独立构建中复现。任一场景不得比基线慢超过 3% 或 50ms，取更大者。
3. **所有候选先测量。** 只把达到预算的优化合入 `fork/main`；未达到门槛的候选记录为不做。
4. **延后不能转嫁等待。** 当前文档需要的模块必须在编辑器可用前加载；按需模块第一次使用的额外等待不得超过 50ms。设置页和常用语言可以在首帧后空闲预取，罕见语言、KaTeX 和主题编辑器按需加载。
5. **工作区按可见性决定。** 侧边栏启动时关闭，工作区扫描可以延后；侧边栏自动展开时保持当前同步扫描，避免出现先空后填的可见变化。
6. **字体列表使用持久化缓存和后台刷新。** 已保存的字体和字号立即生效；系统字体枚举不阻塞可交互时间。
7. **不重写编辑器核心。** 本轮不重构 Markdown 解析器、语法标记、装饰器或 ProseMirror 插件。如果这些部分实测占比超过 30%，另开 Spec。
8. **Windows 是主要性能目标平台。** macOS 和 Linux 保证功能不倒退，不同时承诺相同百分比。
9. **CI 只检查确定性预算。** 首屏资源口径固定为 `index.html` 显式引用的全部资源：入口 module script、其静态依赖 chunk 和全部 stylesheet。预算按阶段 2 基线加 5% 余量设为：首屏 JS 原始体积不超过 2.45MB、首屏 JS Gzip 不超过 810KB、首屏 CSS Gzip 不超过 38KB。原先的 2.1MB / 720KB / 30KB 保留为减体积目标，不作为当前 CI 门槛。启动耗时使用人工基准，不能用 CI 时间断言替代。
10. **内存增长有上限。** Windows 上只统计 Browser 与 Tab 两个进程的私有字节，排除 GPU 和 Utility 进程；峰值内存增加不超过 30MB，典型启动增加不超过 10MB。
11. **每项优化独立提交。** 不使用永久功能开关；收益不达标或出现回归时，可以单独回滚。

## 后果

- 19% 是当前可验收的下限，25% 是挑战目标；未达到 25% 不等于工作失败，但必须明确记录实际收益。
- 体积预算按当前基线加 5% 设置，旧的更小数字只作为减体积方向，不让 CI 一上线就失败。
- Windows 内存判据只覆盖 Browser 与 Tab 的私有字节，不能直接外推到 macOS 或 Linux。
- 启动优化会引入少量空闲预取、缓存和基准代码，结构比一次性同步初始化更复杂。
- 字体列表在刷新完成前可能短暂显示上次缓存，但必须自动更新，不能要求用户重新启动。
- 工作区延后只适用于启动时关闭的侧边栏；自动展开场景仍需承担同步扫描成本。
- 性能收益以 Issue #18 的 P50/P95、体积和内存数据为准，没有达到门槛的候选不进入主分支。
- 性能工作只在 `runningwaterpro/milkup` 推进，不与上游 PR 绑定。
