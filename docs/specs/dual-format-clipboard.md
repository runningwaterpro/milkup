## Problem Statement

在 Milkup 编辑器中选中内容并复制后，粘贴到邮箱、Word 等富文本目标时，得到的是 Markdown 源码，而不是渲染后的格式（标题、加粗、列表、表格等全部丢失）。

用户需要与 Typora 等编辑器一致的体验：一次复制，目标应用按自身能力选择格式——邮箱/Word 显示格式，记事本/Markdown 编辑器仍是源码。

---

## Solution

在编辑器内复制/剪切时 **默认双写** 剪贴板：

| 格式 | 内容 | 典型目标 |
|------|------|----------|
| `text/plain` | 选区 **Markdown** 源码 | 记事本、VS Code、其它 md 编辑器 |
| `text/html` | 选区 **渲染 DOM** 序列化的语义 HTML + 邮箱安全内联样式 | 网页邮箱、Outlook、Word |

暗色主题下使用 **浅色基线** 计算样式后再内联，避免深色背景/浅色文字进入邮件。

对齐的是 Typora 的 **复制出口行为**，不复刻其编辑器或强制其私有回贴属性。

---

## User Stories

1. 作为邮件作者，我希望把含标题、粗体、列表的内容粘贴到网页邮箱后仍有格式，以便直接发送协调日报类邮件。  
2. 作为 Markdown 编辑者，我希望同一份复制粘贴到记事本或 VS Code 时仍是 Markdown 源码，以便继续用纯文本工具处理。  
3. 作为表格作者，我希望复制渲染后的表格粘贴到 Word 得到可编辑的真表格，而不是 `| a | b |` 源码行，以便在 Word 中修改（关联 #252）。  
4. 作为表格作者，我希望复制表格粘贴到邮箱时保留表格结构，以便收件人直接阅读行列。  
5. 作为暗色主题用户，我希望复制到邮件的内容不携带深色背景等编辑器样式，以免在浅色邮件客户端中难以阅读。  
6. 作为正文作者，我希望链接以可点击的 HTML 链接进入邮箱，而不仅仅是裸 URL 或 markdown 链接语法。  
7. 作为正文作者，我希望有序/无序列表在邮箱中呈现为列表，而不是带 `1.` / `-` 的纯文本堆叠。  
8. 作为代码编写者，我希望代码块与行内代码在支持的目标中以等宽、可辨识的方式粘贴，以便审阅。  
9. 作为含图作者，我希望 HTML 中保留 `img` 且 src 可访问（远程 URL，或本地可转为 data URL 时转换），以便邮件尽量显示图片。  
10. 作为含图作者，当某张图无法转换/加载时，我希望仍保留该 `img` 节点与原 src，而不是整图被静默删除。  
11. 作为引用/强调内容的作者，我希望引用块与下划线等行内强调在富文本目标中保持可识别的格式。  
12. 作为只使用默认快捷键的用户，我希望 `Ctrl+C` / 剪切即可得到双格式，而无需先找“复制为富文本”菜单。  
13. 作为需要纯 Markdown 的用户，我接受默认双写；若将来需要“只复制 Markdown”，可另开功能，不阻塞本需求。  
14. 作为贡献者，我希望先在自己的 GitHub fork 上开发与自测，验证通过后再向 `Auto-Plugin/milkup` 上游提 PR，以便控制变更风险。  
15. 作为维护者，我希望实现落在当前 main（Milkdown/Crepe）路径上，以便现网用户尽快受益；v2 另行移植。  
16. 作为维护者，我希望验收不依赖擅自关闭他人 issue；表格达标后在 #252 评论结果，由维护者决定是否关闭。  
17. 作为从外部富文本粘贴进 Milkup 的用户，我不希望本功能改变粘贴行为（那是另一方向的需求）。  
18. 作为导出 PDF/HTML/Word 的用户，我不希望本功能顺带重构导出实现导致回归。  
19. 作为使用公式或 mermaid 的用户，我理解第一版可暂不保证其邮件保真，文字与表格/代码优先。  
20. 作为 QA，我希望有一份固定的“复制 → 三种目标”手工清单，以便每张票合并前可重复验收。

## Implementation Decisions

### 产品与交互

- 编辑器内 **默认双写**（复制/剪切），对齐 Typora 出口心智；不把“复制为富文本”做成第一版必选入口。  
- **不**实现“显式只复制 Markdown”菜单（后置另票）。  
- 第一版范围以 DoD **B5-b** 为准：文字类 + **表格** + **代码块**；公式、mermaid **后置**。

### 剪贴板与 HTML

- 渲染进程对选区写入 `text/plain` 与 `text/html`；Windows 下由系统/浏览器打包为 **CF_HTML**，不手写 `StartHTML` 头，除非实测失败。  
- **主路径：** 选区 **渲染 DOM → HTML**（等价所见即所得），**不用** Markdown→再解析 HTML 作为主路径。  
- **样式策略：** 以计算样式为底 + **邮箱安全收敛**（去掉仅编辑器使用的属性；避免把无害于编辑器但有害于邮件的样式原样带出）。  
- **浅色基线（已定）：** 暗色主题下复制时，按邮件友好的浅色基线生成/覆盖关键样式后再内联。  
- **不强制** Typora 私有 `mdtype` / `md-inline` / `cid` 等属性；可作为后续可选增强。

### 图片

- HTML 保留 `img`，src 使用可访问地址（http(s)，或可转换时的 data URL）。  
- 转换/加载失败：**保留原 src 节点**，不删除该 `img`（B9-a）。

### 架构与落点

- 落点：**当前 main + Milkdown/Crepe**；v2 后移植，不阻塞本 spec。  
- **薄 prefactor：** 从现有“导出时克隆并内联样式”的能力中抽出可共用逻辑，供复制 payload 复用；**不**借机重构导出行为。  
- **测试主 seam（已确认）：** 纯函数级 `buildClipboardPayload`（或等价命名）：输入选区 Markdown + 选区根节点（或等价片段），输出 `{ plain, html }`。  
- **次 seam：** copy/cut 适配层（调用 payload 后 `clipboardData.setData`）；可用合成 ClipboardEvent 薄测，或 MVP 初期手工。  
- **不**将 Electron 应用菜单、整页 Crepe 启动作为自动化测试 seam。  
- 菜单 `role:copy`：**先不动**（B8-a）；若实测导致丢 HTML，再允许改菜单/IPC（B8-b 升级路径）。  
- 引入测试运行器时采用 **最小 vitest（+ DOM 环境）**，只断言 payload 外部行为，不断言内部实现细节。仓库当前无测试基建，此为新建先例。

### 发布与协作流程

- **贡献：** 开发者 **fork** 上游仓库到个人账号 → 在 fork 上分支开发与自测 → 验证通过后向 `Auto-Plugin/milkup` 提 **Pull Request**。  
- **票据：** 按 B7-c，先写入本地 `.scratch/<feature>/issues/`，人工确认后再发布到 GitHub。  
- **Spec 本文件：** 按当前选择 **仅本地保存**，不自动开 GitHub issue。  
- 关联 issue 评论/关闭策略见 A9（不擅自关 #252）。  
- 标签约定：`ready-for-agent`、`enhancement`（`ready-for-agent` 在上游尚不存在，发布票据时需创建）。

### 建议票据切分（B6-b，阻塞边）

1. **双写骨架** — 段落 + 粗体即可：plain=md，html 可进网页邮箱；主 seam 单测可绿。无阻塞。  
2. **块级完善 + 浅色基线** — 标题、列表、链接、引用等 + 暗色浅色策略。阻塞：票 1。  
3. **表格 + 代码块 + 图片 src** — 凑齐 B5-b（含 Word 真表格）。阻塞：票 2。

## Testing Decisions

### 什么是好测试

- 只断言 **外部行为**：给定输入 payload 后，`plain` 是否为预期 Markdown、`html` 是否含预期语义标签与关键内联样式、表格是否存在 `<table>` 等。  
- **不断言**：内部函数调用顺序、私有类名实现细节、Electron 菜单状态。  
- 邮箱/Word/记事本端到端体验以 **固定手工清单** 为准，不作为第一版强制自动化。

### 测什么 / 在哪测

| 层 | 对象 | 方式 |
|----|------|------|
| 主 | `buildClipboardPayload`（选区→plain+html） | 单测（vitest） |
| 次（可选） | copy/cut 适配层 setData | 合成 ClipboardEvent 或手工 |
| 人工 | 网页邮箱、Word、记事本 | B5-b 验收清单 |
| 回归 | 导出 HTML/PDF/Word | 抽查，防止薄抽共用时回归 |

### 先例

- 仓库 **尚无** 单元测试先例；本功能引入的最小 vitest 配置即为先例。  
- 语义/样式参考可对照剪贴板侧 Typora CF_HTML 实测结构（见 grilling 时期导出的 fragment 样例，仅作对照，不作为脆弱快照锁死全部属性）。
